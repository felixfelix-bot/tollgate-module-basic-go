# Router wallet seed at rest: accept `0600` today, encrypt before real money

**Decided:** 2026-10-26. Scope: `src/tollwallet/cdk_wallet.go` and the router
deployment of the wallet (in-process CDK or the sidecar).

**Status:** accepted as an interim position, with a named trigger for the fix.

## The measured situation

- `loadOrCreateMnemonic` (`src/tollwallet/cdk_wallet.go:46-67`) writes the seed
  to `<walletPath>/cdk-wallet-mnemonic.txt`, directory `0700`, file `0600`,
  generated by `cdk_ffi.GenerateMnemonic()`.
- The seed **is** the key material: losing it forfeits the wallet; reading it
  drains the wallet.
- It is **plaintext at rest**, and the value lives in a Go `string`, so it is
  never zeroised. Both facts were already recorded in the wallet-migration
  research; this ADR makes the acceptance explicit rather than implied.

## Decision

1. **The router's seed stays on the router.** No network vault in the boot path,
   no fetch over the mesh at startup, no dependency on OpenBao being reachable.
2. **Encrypt it before the rail carries meaningful value.** Preferred order:
   a) `systemd-creds` encrypted with the device TPM2 key where one exists;
   b) a passphrase-derived key (argon2/scrypt) held `0600` in a root-only path,
      decrypted into a tmpfs file that is unlinked after load;
   c) an OS keyring — only if it survives reboot unattended.
3. **Until (2) lands, the accepted mitigation is:** `0600`, a dedicated service
   user, no copies of the file in any backup, repository, log, or support
   bundle, and no second process running as the same user that does not need it.
4. **A copy may be kept in OpenBao** at
   `secret/data/fleet/router-wallet/<device-code>` for recovery — as an
   *additional* copy, never as the thing boot depends on. See
   `fiat-rail-secret-custody-decision.md`.

## Why this is accepted now and not fixed first

- The seed's blast radius is **funds in that wallet**, not issuance. A stolen
  router drains what that device accumulated; it cannot mint.
- The realistic compromise path is physical: pull the flash, read the file. A
  TPM-backed credential meaningfully raises that bar; a vault fetch does not
  (the attacker with the device has the network credentials too).
- Deferring is only acceptable because the value at risk is small until the rail
  is live. That is the trigger: **before the first real customer payment**, item
  (2) must be implemented and verified.

## Verification (must be run, not assumed)

- Read the seed as the service user → succeeds; as any other unprivileged user →
  fails.
- Reboot → the wallet keeps the same address (the seed survived).
- Restore from the escrow copy on a clean host → **same address**. If it does
  not, the escrow is not an escrow.
- After the encryption change: confirm no plaintext seed is left on disk
  (`grep -r` over the wallet path and `/tmp`), and that a power-loss during
  startup does not leave a decryptable copy in a temp file.

## Rejected alternatives

- **Fetch from OpenBao at boot.** Self-inflicted outage risk on a field device;
  see the custody ADR.
- **Bake the seed into the image or config bundle.** Turns every firmware copy
  into a wallet copy, and makes rotation impossible.
- **Encrypt with a key stored beside the ciphertext.** Raises no bar against the
  threat that matters here (physical access) and creates a false sense of
  safety.
