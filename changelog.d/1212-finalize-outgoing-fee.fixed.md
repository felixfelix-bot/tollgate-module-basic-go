- **An outgoing payment's actual fee can no longer poison the wallet budget.** `Advance` takes no `Budget` argument, so driving an outgoing operation to `paid` through it recorded whatever `uint64` the caller passed as `ActualFeeMSat`. `outgoingCostLocked` counts that number for resolved sends, so one fee above the limit — the verify response is the natural source of an unbounded value — refused every later `Prepare` for that wallet, a durable denial of the payment path. `FinalizeOutgoing` is now the only route for `submitted`/`unknown → paid`, and that exclusivity is **enforced**: `Advance` refuses `outgoing → paid` outright, exactly as it already refuses `outgoing prepared → submitted`. `FinalizeOutgoing` rechecks the current period budget with the actual fee before recording it, still accepts a verified over-reserve that fits, and records nothing when the fee does not.
